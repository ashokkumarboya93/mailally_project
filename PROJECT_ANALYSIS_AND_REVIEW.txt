1. EXECUTIVE SUMMARY & PROJECT OVERVIEW
===============================================================================
MailAlly Enterprise is a modern, high-performance, enterprise-grade multi-tenant 
SaaS platform designed for automated email marketing, audience segmentation, 
multi-provider campaign delivery, real-time analytics, and AI-assisted email content 
generation.

The platform has been designed and built from scratch as a modular, production-ready 
full-stack application consisting of:
  • Spring Boot 3.x / Java 21 Backend (REST API with 18 domain modules)
  • React 19 / Vite 6 Frontend (Single Page Application with 15 SPA modules)
  • MySQL 8.0 Database (Relational persistence with multi-tenant org isolation)
  • Pluggable Email Engine (Supporting SMTP, AWS SES, Brevo providers)
  • AI Copywriting Module (Supporting Mock, OpenAI, Claude providers)
  • Comprehensive Product Blueprint (`blueprint.md`) and Documentation

4. HOW THE PROJECT WORKS INTERNALLY (CORE MECHANISMS & FLOWS)
===============================================================================

-------------------------------------------------------------------------------
4.1 MULTI-TENANT ORGANIZATION ISOLATION ENGINE
-------------------------------------------------------------------------------
MailAlly uses standard organization-level data partitioning:
1. Every major database entity (Campaign, Contact, Template, Segment, Notification, AuditLog) 
   contains an `organization_id` foreign key.
2. When an authenticated user submits a request, the system extracts their `organizationId` 
   from the validated JWT claims.
3. Every JPA Query / Service layer operation includes a mandatory filter:
   `WHERE organization.id = :orgId`.
4. This guarantees strict multi-tenant isolation, preventing cross-organization 
   data leakage.

-------------------------------------------------------------------------------
4.2 AUTHENTICATION & ROLE-BASED ACCESS CONTROL (RBAC)
-------------------------------------------------------------------------------
1. User logs in via POST `/api/v1/auth/login` with credentials.
2. `AuthService` verifies credentials using BCrypt password encoder.
3. Upon successful login, `JwtService` constructs a JWT signed with SHA-256 HMAC containing:
   - Subject (User Email / Username)
   - User ID & User Role (`SUPER_ADMIN`, `ADMIN`, `MARKETER`, `VIEWER`)
   - Organization ID
4. On subsequent requests, `JwtAuthenticationFilter` intercepts the HTTP header:
   `Authorization: Bearer <token>`
5. The filter decodes and validates the token, builds a `UsernamePasswordAuthenticationToken`, 
   and attaches it to Spring's `SecurityContextHolder`.
6. `SecurityConfig` enforces method-level or endpoint-level authority checks.

-------------------------------------------------------------------------------
4.3 PLUGGABLE MULTI-PROVIDER EMAIL ENGINE
-------------------------------------------------------------------------------
MailAlly features an enterprise-grade pluggable email delivery subsystem:

                  +-----------------------------------+
                  |         EmailEngineService        |
                  +-----------------+-----------------+
                                    |
                       Select Provider dynamically
                                    |
                  +-----------------v-----------------+
                  |       EmailProviderFactory        |
                  +-----------------+-----------------+
                                    |
          +-------------------------+-------------------------+
          |                         |                         |
+---------v---------+     +---------v---------+     +---------v---------+
| SmtpEmailProvider |     | SesEmailProvider  |     | BrevoEmailProvider|
|  (Spring Mailer)  |     |   (AWS SES SDK)   |     |   (Brevo REST API)|
+-------------------+     +-------------------+     +-------------------+

Internal Flow:
1. `CampaignServiceImpl` or `EmailEngineService` receives a dispatch request.
2. `EmailRenderer` injects personalization merge tags (e.g. `{{firstName}}`, `{{company}}`) 
   into the dynamic email template.
3. `EmailProviderFactory` resolves the configured active provider (SMTP, AWS SES, or Brevo) 
   for the user's organization.
4. The resolved provider executes the delivery and returns an `EmailSendResult` object containing:
   - `success` (boolean)
   - `messageId` (external provider ID)
   - `errorMessage` / `errorCode` (if failed)
5. Delivery events are logged to the `email_logs` table for real-time tracking.

-------------------------------------------------------------------------------
4.4 DYNAMIC CAMPAIGN SCHEDULER & BACKGROUND EXECUTION
-------------------------------------------------------------------------------
1. Campaigns can be sent immediately or scheduled for future execution.
2. `SchedulerServiceImpl` manages campaign schedules stored in the database.
3. A background task runner (`CampaignScheduler`) periodically evaluates scheduled campaigns:
   - Queries campaigns where `status = 'SCHEDULED'` AND `scheduled_at <= NOW()`.
   - Transitions campaign status to `'PROCESSING'`.
   - Fetches targeted contacts (or evaluates segment rules).
   - Batches recipient lists to prevent memory bottlenecks.
   - Invokes `EmailEngineService` for recipient batch dispatch.
   - Updates campaign status to `'COMPLETED'` or `'FAILED'`.

-------------------------------------------------------------------------------
4.5 DYNAMIC RULE-BASED AUDIENCE SEGMENTATION
-------------------------------------------------------------------------------
1. Instead of static subscriber lists, segments are built using dynamic rules stored in JSON format 
   (e.g., `[{"field":"openRate", "operator":">", "value":"25"}, {"field":"country", "operator":"EQUALS", "value":"US"}]`).
2. `SegmentEvaluator` parses the segment rule set against the subscriber database.
3. Dynamic SQL specifications are built at runtime to filter contacts matching all/any rule criteria.
4. Ensures real-time accuracy without needing manual subscriber list re-imports.

-------------------------------------------------------------------------------
4.6 AI COPYWRITER ENGINE (PROVIDER-AGNOSTIC AI)
-------------------------------------------------------------------------------
1. The AI module (`com.mailally.ai`) accepts prompt requests for:
   - Subject Line Generation & Optimization
   - Email Body Generation (Tone adjustments: Professional, Casual, Urgent)
   - Spam Score Analysis & Improvement Suggestions
   - Campaign Idea Strategy Generation
2. `AiProviderFactory` delegates the prompt to the configured provider:
   - `MockAiProvider` (for local development/testing without API keys)
   - `OpenAiProvider` (OpenAI GPT-4 / GPT-3.5 REST API integration)
   - `ClaudeAiProvider` (Anthropic Claude REST API integration)

-------------------------------------------------------------------------------
4.7 FRONTEND STATE & NAVIGATION FLOW (REACT 19 + VITE)
-------------------------------------------------------------------------------
1. App is bootstrapped in `main.jsx` and wrapped with `AuthProvider` and `ThemeProvider`.
2. `Axios` instance in `src/api/axios.js` automatically attaches stored JWT tokens to all outgoing requests.
3. If an API returns `401 Unauthorized`, Axios interceptors catch the response, clear invalid session tokens, 
   and redirect the user to `/login`.
4. UI uses Tailwind CSS utility classes and Lucide React icons for a dark/light responsive layout.
5. Recharts components dynamically render campaign performance graphs, delivery stats, and open rates.

6. KEY DESIGN PATTERNS & BEST PRACTICES USED
===============================================================================
1. Factory Pattern: Used in `EmailProviderFactory` and `AiProviderFactory` to cleanly instantiate 
   the appropriate strategy at runtime without coupling code to concrete implementations.
2. Strategy Pattern: Pluggable email providers (SMTP, AWS SES, Brevo) and AI providers 
   (Mock, OpenAI, Claude) implementing common interfaces.
3. Repository Pattern: Spring Data JPA interfaces abstracting complex database interactions.
4. DTO / Mapper Pattern: Clean separation between internal database JPA Entities and 
   external HTTP API Request/Response DTOs using Mappers.
5. Stateless JWT Session Security: Scalable token architecture eliminating backend server session state.
6. Layered Architecture: Strict separation of concerns (Controller -> Service -> Repository -> Entity).
7. Modular Component Hierarchy in Frontend: Modular pages, reusable UI components, centralized API client layer.
